## 两块内存：栈和堆

| | 栈 Stack | 堆 Heap |
| --- | --- | --- |
| 存什么 | 基本类型的**值**、引用类型的**地址** | 引用类型的**实际数据** |
| 大小 | 小、固定 | 大、动态 |
| 分配 | 编译期确定，自动回收 | 运行时分配，靠 GC 回收 |
| 访问 | 快 | 慢（要先拿地址再寻址） |
| 有序性 | 后进先出，连续 | 无序 |

**基本类型**（`undefined`、`null`、`boolean`、`number`、`string`、`symbol`、`bigint`）的值直接存在栈上。
**引用类型**（`object`、`array`、`function`）的数据存在堆上，栈上只放一个指向它的地址。

```
let a = 10;
let o = { v: 1 };

        栈                        堆
   ┌──────────┐            ┌──────────────┐
 a │    10    │            │              │
   ├──────────┤            │  { v: 1 }    │
 o │ 0x7f3a…  │ ─────────▶ │              │
   └──────────┘            └──────────────┘
```

## 由此推出的四个行为

### 1. 基本类型赋值 = 拷贝值

```js
let a = 10; let b = a; b = 20;
```

```
1) 基本类型  a = 10   b = 20
```

栈上开了两块独立空间，互不影响。

### 2. 引用类型赋值 = 拷贝地址

```js
let o1 = {v:1}; let o2 = o1; o2.v = 99;
```

```
2) 引用类型  o1.v = 99   o1===o2 → true
```

两个变量存的是**同一个地址**，指向堆上同一个对象。改哪个都一样。

### 3. 重新赋值会切断关联

```js
let p1 = {v:1}; let p2 = p1; p2 = {v:99};
```

```
3) 重新赋值  p1.v = 1   p1===p2 → false
```

`p2 = {...}` 改的是**栈上 p2 那格存的地址**，让它指向一个新对象，原对象没被动过。

**「改属性」和「重新赋值」的区别，是这一整套题的核心。**

### 4. 函数传参：JS 只有按值传递

很多人说「JS 对象是按引用传递」，**这个说法不准确**。JS **只有按值传递**，只不过对象传的是「引用的值（地址）」。

```js
function mutate(o)   { o.v = 'mutated'; }      // 顺着地址改堆上的对象 → 外部可见
function reassign(o) { o = {v:'reassigned'}; } // 改形参这格栈空间 → 外部无感
```

```
4a) 改属性    q.v = mutated
4b) 重新赋值  q.v = orig    <- 外部不受影响
```

如果真是「按引用传递」，`reassign` 里的重新赋值应该会影响外部变量。实测不会——**证明传进去的是地址的副本**。

## 字符串的特殊性

字符串是基本类型，但它的内容通常存在堆上（长度不定），栈上存的是引用。关键在于它**不可变**：

```js
let s = 'abc'; s += 'd';
```

```
6) 字符串    原值 abc  新值 abcd  <- 生成了新字符串
```

任何「修改」都是生成新字符串，原来那个不变。这也是 V8 能对字符串做 **interning**（相同字面量共用一份）的前提。

## 闭包：变量活过了函数调用

正常情况下函数执行完，它的执行上下文出栈，局部变量被回收。但如果内部函数引用了外层变量，那些变量会被挪到堆上，跟着闭包活下来：

```js
function counter(){ let n = 0; return () => ++n; }
const c = counter();
```

```
5) 闭包       1 2 3   <- n 没被回收
```

`counter` 早就返回了，`n` 却还在累加——它已经不在栈上，而在堆里由闭包持有。**这正是闭包会造成内存泄漏的原因**：只要闭包还被引用，它捕获的变量就一直占着堆内存。

## V8 的堆是怎么分代的

V8 按「大部分对象都是朝生夕死」这个观察把堆分成两块：

| 区域 | 装什么 | 回收算法 |
| --- | --- | --- |
| **新生代 Young** | 新建的小对象，通常 1–8MB | **Scavenge**：等分成 From / To 两个 semispace，存活对象复制到 To，然后两者互换。快，但浪费一半空间 |
| **老生代 Old** | 从新生代晋升的、大的、长寿的对象 | **Mark-Sweep**（标记清除）+ **Mark-Compact**（标记整理，解决碎片） |

**晋升条件**：一个对象在新生代里经历过一次 Scavenge 还活着（或 To 空间使用超过 25%），就被移到老生代。

现代 V8 还有 **Orinoco** 的增量标记、并发标记、并行清理，把 GC 停顿切碎以免长时间卡住主线程。

## 判断「能不能回收」用的是可达性，不是引用计数

现代 JS 引擎用 **可达性分析**：从一组 GC Roots（全局对象、当前调用栈上的变量、活跃闭包等）出发遍历，**遍历不到的就是垃圾**。

这和早期 IE 用的**引用计数**有本质区别——引用计数处理不了循环引用：

```js
function leak() {
    const a = {}, b = {};
    a.ref = b; b.ref = a;   // 互相引用，计数永远不为 0
}
```

引用计数下这两个对象永远回收不掉；可达性分析下，`leak()` 返回后从 GC Root 到达不了它们，正常回收。

> iOS 的 ARC 正好是引用计数方案，所以它**确实**有循环引用问题，要靠 `weak`/`unowned` 手动打破——参见 [ios-interview.md 第 79 题](../../ios-interview.md#79-什么是循环引用如何解决-)。两套内存管理机制的取舍对比，是个不错的延伸话题。

## 常见的四类泄漏

| 类型 | 例子 | 根因 |
| --- | --- | --- |
| 意外全局变量 | 忘写 `let`，`function f(){ x = 1 }` | 挂在全局对象上，永远可达 |
| 忘记清理的定时器 | `setInterval` 没 `clearInterval` | 回调闭包一直被引用 |
| 脱离 DOM 的引用 | 变量还存着已 `removeChild` 的节点 | JS 侧仍可达，DOM 树释放不掉 |
| 闭包滥用 | 闭包捕获了大对象却只用其中一个字段 | 整个对象跟着活 |

排查手段：Chrome DevTools 的 **Memory → Heap snapshot**（比对两次快照的 Delta）和 **Allocation instrumentation on timeline**。
