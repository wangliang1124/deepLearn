## 演进主线

```
回调函数  →  Promise  →  Generator + co  →  async/await
   ↓            ↓             ↓                 ↓
 嵌套地狱    链式扁平      同步写法但要驱动     语言级语法糖
 信任问题    状态机可靠     用得少              事实标准
```

一句话概括这条线：**每一步都在解决「异步代码难以像同步代码那样读和写」这一个问题。**

## 1. 回调函数

```js
cb('A', 1, (e, a) =>
  cb('B', 1, (e, b) =>
    cb('C', 1, (e, c) => console.log(a, b, c))));
```

```
回调嵌套结果: A B C
```

**优点**：最原始、零依赖、开销最低。
**缺点**：

| 问题 | 说明 |
| --- | --- |
| **回调地狱** | 嵌套层数 = 异步步骤数，横向缩进失控 |
| **错误处理割裂** | 每层都要 `if (err) return cb(err)`，漏一处就静默失败 |
| **无法用 try/catch** | 回调在另一个事件循环 tick 里执行，外层 try 捕获不到 |
| **控制反转** | 把回调交给第三方库，它调几次、什么时候调、传什么参数，你都控制不了 |

最后一条是最根本的——**信任问题**。Promise 真正解决的其实是这个。

## 2. Promise（ES6）

```js
p('A').then(a => p('B').then(b => [a, b]))
      .then(([a, b]) => console.log(a, b));
```

```
链式: A B
```

**优点**：

- **状态机不可逆** —— `pending → fulfilled/rejected` 只能转一次，且**只能转一次**，从机制上杜绝了「回调被调用多次」
- **链式扁平** —— `.then()` 返回新 Promise，把嵌套变成平铺
- **错误冒泡** —— 一个 `.catch()` 可以兜住整条链上任意一环的错误
- **组合能力** —— `all` / `race` / `allSettled` / `any`

**缺点**：

- 仍然是**回调风格**，只是位置从参数挪到了 `.then` 里
- 链条长了照样难读，尤其是需要拿到中间某一步的值时（上面那个嵌套 `p('B').then` 就是这个毛病）
- **无法取消**（这是 Promise 最被诟病的设计，要靠 `AbortController` 补）
- 一旦开始就会执行，不是惰性的

四个组合方法的区别值得记牢：

| 方法 | 何时 resolve | 何时 reject |
| --- | --- | --- |
| `all` | **全部**成功 | **任一**失败（快速失败） |
| `allSettled` | **全部**结束（无论成败） | 从不 reject |
| `race` | **第一个**结束的（成败都算） | 同左 |
| `any` | **第一个**成功的 | 全部失败（抛 `AggregateError`） |

## 3. Generator + 执行器（ES6）

```js
function* gen() {
  const a = yield p('A');
  const b = yield p('B');
  return [a, b];
}
co(gen);   // 需要一个执行器来驱动
```

**优点**：第一次让异步代码**长得像同步代码**，`yield` 处暂停、恢复。
**缺点**：

- **必须配执行器**（`co` 库或自己写递归 `next()`），语言本身不会自动驱动
- 语义上 Generator 是「迭代器协议」，拿它做异步属于**借用**，概念不匹配
- 写法别扭，`function*` + `yield` 不直观

**现状：基本被淘汰**。了解它的价值在于——`async/await` 的底层就是 Generator + 自动执行器，Babel 转译 `async` 函数就会生成类似 `co` 的 `_asyncToGenerator` 辅助函数。

## 4. async/await（ES2017）

```js
const a = await p('A');
const b = await p('B');
```

```
await: A B
```

**优点**：

- 同步写法，**可以用 `try/catch`**，这是相比 Promise 最大的体验提升
- 单步调试符合直觉
- 本质仍是 Promise，和现有生态完全兼容

**缺点**：

- ⚠️ **最容易写出「假异步」** —— 见下节
- 顶层 await 有模块限制（需 ESM）
- 错误处理写多了 `try/catch` 也啰嗦，有人退回 `.catch()` 或 `[err, data]` 元组风格

### 最重要的坑：串行 vs 并行

```js
// ❌ 无依赖关系却串行等待
await slow(60); await slow(60); await slow(60);

// ✅ 并行发起，一起等
await Promise.all([slow(60), slow(60), slow(60)]);
```

```
串行 3×60ms 实际: 186 ms
Promise.all 实际:  62 ms
```

**3 倍差距。** `await` 会**真的停在那里**，后面的请求根本还没发出去。只要几个异步操作之间**没有依赖关系**，就该用 `Promise.all` 并行。

这是 async/await 最常见的性能问题——因为它写起来太像同步代码，容易忘记每个 `await` 都是一次真实的等待。

## 事件循环：宏任务与微任务

不管用哪种方案，底层都归事件循环调度：

```js
setTimeout(() => order.push('setTimeout(宏)'), 0);
Promise.resolve().then(() => order.push('Promise.then(微)'));
queueMicrotask(() => order.push('queueMicrotask(微)'));
order.push('同步代码');
```

```
执行顺序: 同步代码 → Promise.then(微) → queueMicrotask(微) → setTimeout(宏)
```

规则：**同步代码 → 清空所有微任务 → 取一个宏任务 → 再清空微任务 → ……**

| 类型 | 有谁 |
| --- | --- |
| **宏任务** | `setTimeout`、`setInterval`、I/O、UI 渲染、`setImmediate`(Node) |
| **微任务** | `Promise.then/catch/finally`、`queueMicrotask`、`MutationObserver`、`process.nextTick`(Node，优先级更高) |

⚠️ **微任务会被一次性清空**，所以微任务里再产生微任务会继续在本轮执行——无限递归的微任务能**饿死宏任务**，页面直接卡死。

> 仓库里有可运行的顺序演示：[async-execution-order.js](../../async-execution-order.js)，
> 以及用 Generator 模拟 async/await 的实现：[handwritten-async.html](../../handwritten-async.html)。

## 怎么选

| 场景 | 用什么 |
| --- | --- |
| 绝大多数业务代码 | **async/await** |
| 多个独立请求 | **`Promise.all`**（或 `allSettled` 容错） |
| 需要超时控制 | `Promise.race` + 定时器，或 `AbortSignal.timeout()` |
| 需要取消 | **`AbortController`**（`fetch` 原生支持） |
| 事件流 / 可取消的复杂流 | RxJS，或 `AsyncIterator` + `for await...of` |
| 老 Node 回调 API | `util.promisify` 包一层 |

## 还在演进

- **顶层 await** —— ESM 里可以直接 `await`，不用包 IIFE
- **`for await...of`** —— 消费异步迭代器，做流式处理
- **`AbortController`** —— 补上了 Promise 缺失的取消能力
- **`Array.fromAsync`**（ES2024）—— 把异步迭代器收成数组
- **`Promise.withResolvers`**（ES2024）—— 不用再写 `let resolve; new Promise(r => resolve = r)` 这种别扭代码
